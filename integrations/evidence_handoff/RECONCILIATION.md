# 同じ原票で完了状態を再照合する

PR #9 の[受信契約](README.md)に、初回検証が失敗した場合の再照合を加える。対象の同定には元応答の案件ID、型を含む版、各欄の正式な対象名、同じ瞬間を表す `as_of` が必要。業務に使う最新の直接観測を信頼済みの原票から得る。受信した参照IDのなかに別案件・別版が混じった場合でも、対象そのものが確定していれば正しい参照を原票から取り直せる。

| 受信時の状況 | B1の処理 |
|---|---|
| 初回の状態・根拠とも有効 | B0の判断を使用 |
| 対象は正しいが、状態・根拠が原票に合わない | 同じ時点の原票を最大1回取得し、問題のあった欄ごとに照合。両欄が該当しても取得は1回 |
| 原票上の全必須チェックが完了 | 取り直した証跡で完了を検証し、その欄に依存する操作を再判定 |
| 直接観測が未完了を示す | `open` を記録し、当該欄を必要とする操作を保留 |
| 根拠が不足、最新観測が矛盾、識別不能な証跡がある | 回復できなかった理由を記録し、保留 |
| 読み取り失敗・同じ締切で証跡が改変された・案件等の識別情報が不一致 | 該当欄を保留。片欄だけで成立する別の操作は、その欄の確認結果に従う |

`at`（発生）と `available_at`（到着）のいずれかが締切を過ぎた行は、訂正の根拠に使えない。締切後にIDが再利用されても締切内の根拠を隠さない。同じ締切で見えている台帳内の同一IDには一意性を求める。二つの時点の状態変化と、同一時点における誤判定の訂正は区別する。

## 回復と再受信の実行例

原票は南浜分室への図書配送。3箱の受領を確認済みで、報告に必要な冊数の別紙は未着。例の[元応答](examples/misreported-open.json)は業務欄を誤って `open` と宣言している。リポジトリのルートで以下を実行する。同じコマンドを繰り返すと、登録済みの操作を確認できる。

```sh
run_dir="$(mktemp -d)"
python3 -B -m integrations.evidence_handoff.reconcile \
  integrations/evidence_handoff/examples/case.json \
  integrations/evidence_handoff/examples/misreported-open.json \
  --ledger "$run_dir/plans.sqlite"
```

初回のB0は3操作を保留。B1は業務欄だけを再照合し、配送後処理 `advance_operation` を `newly_planned` に記録する。報告の保存とクローズは保留される。同じ台帳での再受信は `already_planned` に配送後処理を記録し、新規予定は0件。台帳のキーは案件・版・判定時点・操作・その操作が依存する対象名を含む。CLIはローカルSQLiteを使い、1回の受信で追加する操作をトランザクションで登録する。Pythonから複数回受信する場合は同じ `PlanLedger` を渡す。

`B0.fields` と `B1.original_response` が最初の検証と宣言を保存し、`B1.reconciliation.fields` には元エラーの検出、再照合の発火理由、取得した根拠、訂正結果が残る。`B1.fields` と `B1.actions` は後続処理に使用した値と最終判断。手順の[評価と失敗記録](../../evals/kuro-v04-reconcile/README.md)には各操作の誤実行・誤保留も含む。
