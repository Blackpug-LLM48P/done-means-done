# DMDの敵対的検証と改善案

**DMD v0.4の本体追記は見送る。状態を機械で読む呼び出し元では、報告の作成と対象業務の完了を別々に扱う。** たとえば配送の引継ぎでは、照合を終えて正しい未配達一覧を渡した時点で報告は完成する。全便の配達は続いている。本文がこの違いを正しく伝えても、対象名のない単一の `state` だけから、後続処理はどちらの状態かを決められない。

## 呼び出し側の修正を試す

1. **欄が一つの場合は、何の状態かを依頼側で指定する。** 探索用の同じ2案件で、`state` が「締切時点の全便の配達」か「照合報告の作成」かを一文で指定。58件中2件が残った案件で、現行版・追記版ともに前者は `open`、後者は `complete` となった。配達済み49/49の対照も合わせ、状態と件数・荷番は8回答すべてで一致した。[指示と設計](design/target-control.md)・[全8回答の照合結果](results/target-summary.json)
2. **両方を使う場合は、呼び出し側が現場の対象名を渡し、欄を二つにする。** `report_state` は依頼された照合・報告が終わったか、`operation_state` は対象業務が指定時点で完了または実行可能か。本文は件数・残件・受け手が取れる行動を伝える。元のv0.4を使用して既知の12件を再実行すると、2欄とも12/12で期待値と一致し、6件では「報告完了・業務保留」が区別された。本文は依頼を12/12で満たし、より厳しい作者必須事項は前と同じ42/43。追加の2欄の再試験では、JSONの最上位が一方はID付きオブジェクト、もう一方はID付き行の配列だった。両方とも依頼が指定した3項目を含む。自動連携で片方だけを受ける場合は、最上位の形式も契約に含める。[二欄の依頼文](design/two-states.txt)・[対象名](design/business-targets.json)・[二欄の再試験](results/two-states-summary.json)

この12件では全てで報告が完成できた。報告自体が未完のケースは、別作者の新作4件で検査した（下記）。

## 適用する改善案

- 後続が読むのが業務の可否だけなら、既存の一欄に対象と時点を明記する。「全便が締切時点で受領済みか」のように、読み手が判定を一つに絞れる形にする。
- 報告の作成と業務の可否を別々に利用する連携では、二欄に分け、`operation_state` が指す業務を一つだけ渡す。虚偽の確定を作らず、記録の不足と実際の失敗を本文に残す。図書の例で言えば、配送後に残っているのは冊数内訳の取得で、配送のやり直しではない。
- 一欄のままDMD本文に一般的な注意を追加する案は採用基準を満たさなかった。上記の呼び出し側仕様は利用例として提示する。現行版の通常の自然文報告に追加出力を義務づける根拠は得られていない。

## 検証範囲と再現

すべてGPT-6.2 AstraのUltra指定によるシナリオ試験。モデルの新規セッションは、探索2、未見比較6、既知の対象指定4、二欄の再試験2、新作4を使った対照4。案件は探索8、確認12、新作4の計24件。モデル回答の照合には、実運用の人による理解度や自動処理が起こした結果を含めない。原票とコードは再読できるが、モデルの新たな出力の同一性を意味しない。

主試験44回答は2名のモデルが条件名を伏せて独立に判定。フラグの不一致は1件で、3人目が裁定した。二欄の再試験は別の二重採点と2件の裁定を実施した。記述問題は依頼・原文と作者キーを区別し、正解に含まれる識別子まで一律に必須とした場合の取りこぼしも公表した。探索と未見の原文・キーは先に固定、回答者は担当パケットだけを読む指示。OSで遮断した実験ではない。手作りの対の一部は決定的な記録と下書きの両方が変わる。配達の対は生成規則を共有する別台帳。最終の新作比較では業務対象名以外の入力が一致する。
