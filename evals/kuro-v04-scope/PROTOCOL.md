# 完了報告の版と確認作業の一致を試す

前回の公開Q08では、r3の部屋番号を目視照合した根拠としてr2の目視照合が首位になった。その行を外すと、r3のPDFを開いた記録に移った。この例を開発上の動機とし、今回の比較は別々の担当者が新しく作る6案件で実施する。

## 先に固定する内容

1. 事務と技術運用を別の作者へ割り当てる。各3案件・各5問、計30問。入力は案件中の記録行（ID・原文・出所）と、明示された版に関する質問・肯定形の主張。作者は各主張について、単独で直接の裏付けになる全行IDを正解とし、該当がなければ空集合とする。採点前に作者とは別の読者も全件を読み、独立に正解を付ける。相違・曖昧さは原票とともに残す。
2. 検索手法の担当には新案件を渡さない。同じBM25スコアで出所のみ、出所＋版、出所＋確認作業、出所＋版と確認作業の4条件を比較する。各条件で、首位のみ検査する方式と、条件を満たす候補から選び直す方式を別集計する。版・作業は原文から機械で取り出す。全条件に同じ作者提供の出所ラベルを渡す。主比較は、従来と同じ「出所のみで首位を検査」と「版・作業まで検査して選び直す」。他6通りもすべて開示する。
3. 別枠で、案件を直接読むモデルの回答を比較する。条件は一行指示、同じ一行指示に対象・版・実施行為・範囲を明示する一文を足したもの、固定v0.4本文。各条件につき2つの新規GPT-6.2 AstraセッションをUltra指定し、1つは事務、もう1つは技術運用の3案件を読む。各案件は各条件1回。各質問には直接支持する行IDを一つ、なければnullを返し、各案件の最後の質問について受け手に送る日本語を1文書く。正解・検索器・他の回答を渡さない。出力形式と依頼文は共通。
4. 実行前に入力・正解・検索器・意味判定への指示のSHA-256を固定する。新案件ではパラメータや語彙を調整しない。モデルの6回答を固定してから作者票・独立票の差を点検し、必要なら条件を伏せた裁定を先に行う。作者正解と裁定正解の両方で再計算できるようにする。凍結後に入力の解釈上の欠陥が見つかった場合も元データを保持する。

## 評価と採否

正解ありを「正しい行／誤った行／根拠なしと回答」、正解なしを「正しく保留／誤った行を提示」に分ける。主比較では各質問の遷移を集計し、救えた誤提示、増えた誤提示、回復した正解、新しく落とした正解を明示する。誤った行の提示と過剰な保留を、単一の正解率で相殺しない。各案件最後の引継ぎ文では、選んだIDと本文の矛盾、未確認と未実施の混同も調べる。判断に十分な記録がない場合に「実行しなかった」と言い切らない。

安全に自動で完了判定できるかは、誤提示が減ることと正しい根拠を落とさないことの両方で判断する。語彙・場面の違いで結果が崩れる場合は、検索器を本体の完了判定に組み込まない。短い追加指示の効果は、同じ入力での一行指示とv0.4の実測と照合する。独立した試行単位は6案件である。30問が実務の頻度を表すとは仮定せず、人間による検証や別モデルへの一般化は扱わない。
