# 版と確認作業を照合すると、完了の根拠を正しく選べるか

**本体への導入は見送る。** 版と作業の両方を必須にした検索器は、新作6案件で、根拠のない主張への誤提示を13件から0件に減らした。同じ変更で、正しく根拠を示せた主張も15件から2件に減った。両条件とも正解は16/30。既知の失敗例では狙いどおりに動いた。

## 新作30問

入力は演奏会プログラム、旅費精算、会議室の照明、上映字幕、返却仕分け機、印刷校正の6案件、計50行。各5問に対し、検索器も全文を読むモデルも案件内の1行を選ぶか、根拠が足りなければ保留する。事務3件と運用3件を別の作者が新規作成。作者票と第三の読み手による独立票は全30問で一致した。根拠ありは16問、根拠なしは14問。2問には単独で十分な行が2件ずつあり、どちらも正解とした。[原文](inputs/cases.json)・[作者票](inputs/author-gold.json)・[独立票](inputs/independent-gold.json)

「首位」はBM25の1位だけを検査し、不適格なら保留する。「選び直し」は同じ順位表で適格な最上位行を採る。全行の出所区分は全条件に与えた。版と作業は検索器が原文から抽出した。[比較規約](PROTOCOL.md)・[検索器の仕様](method/README.md)

主比較では、根拠なしの誤提示13件が正しい保留へ、根拠ありの正しい行13件が保留へ移った。根拠ありで誤った行を提示していた残り1件も保留に移った。正しい行を新たに回復した設問は0件。版だけを検査した条件では、首位のみが26/30だが、選び直すと15/30になった。正しい行を1件拾えた一方、正しかった保留12件に誤った行を添えた。版が同じ行に別の作業が書かれているため、次候補を返せば改善するとはいえない。[全設問の選択行](results/predictions.json)・[案件別・設問別の遷移集計](results/scores.json)

### 原文のどこで分かれたか

- **止めて正解の例。** 演奏会の印刷所あてメールは下書きに保存され、送信は館長の決裁待ちだった。出所だけではその行を「送信した」の根拠に採用した。版と作業を検査すると保留できた（f7k2/u2f、d4j）。
- **止めてしまった例。** 同じ案件の校閲表には「プログラムr3、表紙の開演18:30を主催者の開催要項と目視照合。合致」とある。BM25ではこの行が首位。版は一致したが、固定した作業表現の照合規則がこの書き方を拾えず保留した（f7k2/h4w、m3p）。
- **正しい根拠14問を落とした内訳。** 各正解行を最初に拒否した理由で数えると、主張の作業を抽出できなかったものが5問、要求は抽出できたが正解行の実施表現を認識できなかったものが8問、版が複数あったものが1問。「第3版 → 第4版　反映完了」という更新履歴も最後の理由で落ちた。複数の正解行がある2問も確認した。正解に指定された全18行はどれもBM25が正だった。[抽出結果・全行の順位と理由](results/ranking.json)

## 全文を読んだ場合と引継ぎ文

3条件で全30問の選択行IDと保留が一致した。どの条件にも、単独で主張を支える行がなければnullを選ぶという共通の依頼と、出所ラベル付きの全記録を渡した。一行条件への追加文とv0.4の上積みは、この設計では観測されなかった。各条件につき事務3案件と運用3案件を別セッションに割り当て、各案件1回、計6セッション。すべてGPT-6.2 AstraのUltra指定で実行した。

各案件の最終質問について書いた引継ぎ文は各条件6文、計18文。支持あり9文・支持なし9文。条件名を伏せた別の読み手が全18文を照合し、選択行と主張の矛盾、未確認を未実施とする断定、根拠のない追加事実、裏付けられた答えの欠落をいずれも0件と判定した。[提出原文](results/raw/)・[判定理由](results/handoff-grades.json)・[匿名票の対応](results/handoff-map.json)

## 前回の公開例に戻すとどうなるか

既知のQ07では、全8条件が正しいr2の目視照合を選んだ。Q08で尋ねたのはr3の目視照合。出所だけの条件はr2の照合を選び、版だけ合わせて選び直すとr3の「PDFを開いた」行を選んだ。版と作業の両方を照合すると正しく保留した。r2を候補から取り除いた再実行でも同じ結果だった。語彙統計は前回の14行に固定し、元の公開得点・順位と照合した。この2問は開発時に参照できたため、新作30問の集計から分けた。[既知例の再実行記録](results/public-regression.json)

## 固定記録と再計算

[事前登録](https://github.com/Blackpug-LLM48P/done-means-done/commit/73f58eed754ea754d0e86ec191eb453507873f07) → [新作・両正解票のハッシュ・検索器・依頼文を固定](https://github.com/Blackpug-LLM48P/done-means-done/commit/02d11a2b8d695aaa16c1ab876cdf3c1887bf6faa) → [モデルの6回答を固定](https://github.com/Blackpug-LLM48P/done-means-done/commit/43a60301894ac1cbde3012a3f4f2c541e132a3ee)。その後に正解票を比較し、相違0件のため裁定は不要だった。独立した作者、検索器作成者、回答者、匿名文の判定者はモデルであり、担当資料だけを読む指示で作業した。人手採点、OSによる読取隔離、実案件での完了率測定は行っていない。

このディレクトリでPython 3.12と標準ライブラリを使って実行する。replayは同じ50行で検索を再実行し、各セッションへの入力3ファイルのハッシュを再構成し、保存されたモデル回答を両正解票で再採点する。モデルの再呼び出しは不要。

```sh
sha256sum -c freeze.sha256
(cd results/raw && sha256sum -c hashes.sha256)
python3 -B method/dev_selftest.py
python3 -B method/score.py --self-test
python3 -B method/replay.py --check
python3 -B method/handoffs.py
python3 -B method/public_regression.py | cmp - results/public-regression.json
```

機械照合も追加の一文も、この結果に基づく本体変更は見送った。公開した6案件は以後の回帰検査に使える。ここを見て語彙を追加した検索器の性能は、別に作った案件で測る必要がある。
