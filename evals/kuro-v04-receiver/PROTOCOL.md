# 原票から後続の実行予定までの事前登録

基準はPR #8のhead 12d6803344037edb11d6792ee6fadb2d1409ad1c。同じSKILL.mdのまま、日本語で借用品の受け渡し記録を読み、原票→呼び出し→DMDの応答→ドライランの受付→後続操作の予定／保留を比較する。Aは#8の一欄依頼をそのまま使い、その値を全操作に投影する模擬受付。Bは対象名、判定時点、証跡を持つ二欄と別々の受付条件。両者に同じ構造化原票を同じ順に渡す。比較対象は呼び出しと受信を合わせた差である。

- 主評価は別担当2名が新作した計8案件、各状態組合せ2件。A/Bそれぞれ各案件に新規セッションを1本、計16回答。継続試験は各条件2セッション×4案件、計16回答。一つのセッションへ一案件ずつ順番に投入し、前の回答を確定してから実UUIDを指定して次を再開する。投入順・件数・条件は design/schedule.json に固定。主評価と継続試験はそれぞれ8案件・各条件24操作機会である。
- 出所、スコープ、必須チェックID、版、発生時刻・参照可能時刻、観測の結果は両条件の原票に含む構造化データ。Bの受付はこれらを信頼済みの台帳として扱う。原文からこれらのメタデータを生成する性能は測らない。
- 報告の確定保存は報告完了かつ本文あり、業務完了後の処理は業務完了、案件のクローズは両方かつ本文あり。外部サービスには書かない。下書きの保存はこの経路でいう確定保存に含めない。片方の状態が不正でも依存しない操作は独立に判定する。
- 本文は条件・セッション・状態欄を伏せ、各案件の作者指定の必須事項が実務上伝わるかを二名が独立に採点。重要な未裏付けの追加情報も点検する。フラグ不一致のみ別の担当者が裁定。同じ本文を複数回観測したときは同じ採点を適用できる。二状態は作者票との対比で、誤完了・誤保留・無効を別に扱う。Aの二軸は共通stateの投影。受付の三操作について正しい実行予定・正しい保留・誤実行予定・誤保留を数える。誤った状態出力の検出と、後続の正誤は別に保存。
- 金庫対象の原票・期待値・件数・この基準・受付実装を本試行前に固定。作問者が平文をファイルに残さず公開鍵で暗号化し、平文の正規化SHA-256と暗号文ハッシュだけを事前登録する。秘密鍵は実行環境外で保持。別の8件は開発中の連絡手段で原票の正解が露出しうることが分かったため、未見評価対象から除外した。モデルには担当原票だけを標準入力経由で渡す。さらにOSで実行プロセスから共有作業領域が読めないことを既知の検査ファイルで点検する。復号と採点は全回答・実際の分岐の固定後。
- モデルは同じ公式Codex CLI、GPT-6.2 Astra、推論量Ultra。計時はCLI呼出しの経過時間、受信判定の経過時間、全体の壁時計。各ターンの取得可能なトークン実測を記録。I/Oや起動時間は推論処理だけの時間とは異なる。実回答の再試行を成績の置換に使わない。インフラだけの不成立は別記し、採点対象が欠測なら採用保留。
- PR #8の回帰と、対象違い・版違い・別案件・時点不一致・不足・誤状態・正常系を含む受付の決定論的対照は [別表](design/receiver-controls.md) のとおり。未見の得点に合算しない。
- 採用はBの固定セットで後続の誤実行予定・誤保留が各0かつ本文必須事項の総数がA以上であること。独立と継続のどちらにも適用し、受付の決定論的対照の予期せぬ失敗も別途開示する。案件別の得失も示す。実装を結果開封後に変更した場合の再実行は回帰として分離する。範囲はこの連携一経路。今回以降の課題は提案に留める。

## 実行前の接続確認

原票の構造だけを照合し、記録の対象は `report`・`operation` のキーと正式な対象名を両方受け付けるようにした。応答には正式な対象名を求める。原票の版番号には整数と文字列があり、その型も含めて応答の版と照合する。原票、採点基準、実行順に変更はない。開封前の受信側対照13件を追加し、計60件とした。[追加対照](design/receiver-controls-revision.md)

実行担当の各CLIは別のファイルシステム名前空間で起動する。作業領域はマウントしない。継続試験だけが自分自身のセッションを再開する。隔離・モデル・再開の疎通結果は[事前の実行記録](design/isolation-smoke.json)にある。推論実行前に固定したファイルは[ハッシュ一覧](design/method-freeze.sha256)で照合できる。
